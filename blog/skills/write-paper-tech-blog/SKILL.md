# 论文技术博客写作

这份 Skill 记录本博客目前偏好的写法。写作前先读同仓库的 [SuperGlue 文章](../../articles/superglue/index.md)；若主题涉及估计、标定或较长的数学推导，再读 [重力与加速度计内参文章](../../articles/gravity-accelerometer-intrinsics/index.md)。借鉴它们的叙事方式，不套用章节数、标题或篇幅。

## 找到文章要解释的事

先读原论文的摘要、方法、图表与实验，确定作者试图解决的具体困难、旧做法在哪一步失效、论文把问题重新表述成了什么。用一句话写出文章主线，再为每一段确定它要回答的读者疑问。这个提纲只用于组织写作；正文自然地推进，不出现“立意分析”“本段思想”“段落拆解”等讲义标签。

标题后、正文开篇前必须放置一段 Markdown 引文块（以 `>` 开头），概括文章的主要内容、展开主线和讨论范围。读者应能先通过这段话知道本文要讲什么、哪些内容会简述或留待另文；不能只写论文元信息来代替内容提要。基于论文的文章可在引文块中同时标明作者、年份和论文题目。

引文块之后，正文开头从可想象的场景或实际工程后果进入问题，随后交代方法在完整系统中的位置。让读者先知道为什么需要这个设计，再看模块和公式。引文块是本博客文章的固定组成部分，但不要求复用某一种固定措辞或篇幅。

## 沿着因果链讲方法

- 按“现有信息不足在哪里 → 新增什么信息或约束 → 怎样计算 → 得到什么能力”的顺序展开。标题写具体问题或机制，避免把论文目录直接改写成中文目录。
- 遇到抽象概念，先给一个足够小、可手算或可想象的例子；明确它是讲解用例，还是论文报告的实验。例子不能替代真实方法的条件。
- 公式出现时就解释变量、坐标系、量纲或约束的作用；推导只保留能让关键跳步变得可理解的步骤。解释公式为什么这样写，以及它不能保证什么。
- 区分论文明确给出的结论、由公式直接推出的性质，以及作者自己的机制解释或推测。发现原文符号不一致或适用条件有限时，写明所采用的约定和边界。
- 用连续段落写文章。列表和表格用于真正需要比较的地方，不把每段压成“目标／已知／收束”式提纲。

## 让系列文章彼此衔接

如果新文章属于已有系列，先检查仓库中的相关文章，确认哪些内容已经讲过、当前文章准备深入哪一部分。正文前部应使用站内链接引用最相关的前文，并用自然段说明两篇文章的关系：前文提供什么背景，本文承接或补充什么。只链接实际存在且与当前主题相关的文章，不虚构篇名、链接或尚未发布的后续内容。需要引用多篇前文时，分别说明它们与当前主题的联系，避免堆放无说明的“相关阅读”链接。

若后续文章已经存在，可从当前文章链接到它；若系列仍在撰写中，只建立指向已发布或已落稿文章的链接，不预设未完成文章的路径。站内链接沿用仓库现有相对链接格式，并在落稿检查中确认目标有效。

## 让图和实验承担证据

在架构、注意力、输出效果等关键处，优先选原论文中真正帮助理解的图。可以从论文 PDF 截取原图，存入该文章的 `figures/`，确认裁切没有截断标注、图像在网页宽度下可读，并在图注写清原论文图号、图中对象以及要读出的信息。自绘图适合补足原图没有说明的关系。不要把一页论文截图堆到文章末尾。

实验段落先说明数据、评价指标、比较对象与受控条件，再给有辨识度的数值或图。解释这个实验究竟支持了哪一项主张：整体效果、下游任务收益，还是某个模块的贡献。比较不同前端、训练设置或评估协议时，指出归因限制；定性图展示现象，消融表帮助解释原因，不用单个好看的案例代替总体证据。

收尾回到论文的核心认识和适用边界，例如对前端质量、场景分布或后端几何验证的依赖。参考资料提供能打开的论文页面及必要的 PDF 链接；正文中的数字、图和特殊判断要能追溯到原文。

## 在本仓库落稿

新文章放在 `blog/articles/<slug>/index.md`，图放在同目录的 `figures/`。沿用博客 front matter，写作阶段保留 `draft: true`；用户要求发表时改为 `false`，按仓库现有构建与发布流程执行。写完通读一遍：删掉读者还没获得上下文就出现的术语，检查相邻段落是否在推进同一条主线，并核对所有图片路径和参考链接。
